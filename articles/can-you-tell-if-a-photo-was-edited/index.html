IMAGE FORENSICS & EDITING TRACES

Can You Tell If a Photo Was Edited? What Image Forensics Can — and Cannot — Show

A photo can carry clues about how it was saved, resized, recompressed or handled by software. The useful part is not finding one suspicious-looking clue. It is knowing what to inspect first, how several observations fit together, and where the conclusion has to stop.

Published September 11, 2026 · Updated September 20, 2026 · SIGNA AI Lab
What you will get from this guide
  • A practical order for examining an unfamiliar image instead of jumping straight to an “edited / not edited” verdict.
  • Three common file patterns — camera original, edited export and screenshot — and how their clues can differ.
  • A clear separation between observation, interpretation and what still cannot be proved.

Quick test: which one is the photo we started from?

Before looking at metadata or compression clues, compare A through D. They all come from the same café scene. One is the camera photo used as the starting point; the others went through a normal edit and JPEG export, crop/resize/recompression, or a screen-capture step. If appearance were all you had, which would you choose?

Show the answer and what changed

A is the camera photo used as the starting point. B was given ordinary brightness, contrast and saturation adjustments and exported again as JPEG. C was cropped slightly, resized and saved again as JPEG. D is a landscape screen-capture derivative. All four can look perfectly plausible at a glance.

That is the point of the exercise: visual confidence is not the same thing as forensic evidence. The useful questions begin with file structure, dimensions, metadata, recompression and the rest of the observable workflow traces.

Start by shrinking the question

“Was this photo edited?” sounds binary, but almost every normal image workflow complicates it. Cropping is an edit. Rotating is an edit. A phone can re-save an image. A social platform can resize and recompress it automatically. A screenshot creates a new file from rendered pixels. None of those facts, by itself, tells you that the picture is deceptive.

A better forensic question is: what observable processing or workflow traces are present in the file I have now? That shift matters because image forensics is strongest when it describes evidence before it tries to explain motive.

Observation
“The JPEG shows signs consistent with another encode step.”
Interpretation
“The current file may have been re-saved or processed by a service or application.”
Too far
“Therefore the picture is fake.” The technical observation does not establish that conclusion.

A practical first-pass workflow

1. File format & dimensions
2. Metadata & software declarations
3. Compression / geometry clues
4. Watermark / provenance checks

This order is intentionally boring. It prevents a common mistake: seeing one metadata field or one missing field and letting it dominate the entire interpretation. The file type and geometry give you context; metadata may expose capture or software information; compression and resize clues say something about the present image state; watermark and provenance systems answer their own narrower questions.

Worked example: three files that can look almost the same

The following is an illustrative walkthrough, not a claim that every camera, editor or screenshot behaves identically. The point is to show how the evidence changes depending on the file path.

File A

Camera original

You may see camera model, capture time, exposure data, GPS if enabled, and dimensions that match the capture. None of those fields are untouchable, but together they can describe the current file’s declared capture context.

File B

Edited JPEG export

The visible scene may be unchanged while dimensions, quantization behavior, timestamps or software declarations differ. A software name can support “this application wrote a declaration,” not “this application created the original scene.”

File C

Screenshot

The original file container is no longer being copied. Camera EXIF commonly does not travel into the new screenshot file; the new dimensions and capture context belong to the screenshot process.

SIGNA LAB READING RULE

Do not score clues as guilty or innocent.

Ask whether independent observations agree. A missing camera block plus screenshot-like dimensions may be coherent. A software declaration plus another encode step may be coherent. When observations conflict, that tension is itself useful — but it is still not a universal authenticity verdict.

Metadata: useful context, weak as a stand-alone verdict

EXIF, XMP, IPTC and format-specific metadata can expose camera settings, timestamps, software declarations or workflow records. A software tag can show that an application wrote or preserved a value in the current file. It does not establish who created the image or every edit that occurred.

Missing metadata is just as ambiguous. Screenshots, privacy exports, messaging services, converters and ordinary editing tools can remove it. This is why the useful question is not “Is EXIF present?” but “Which structures are present, what do they say, and are those observations compatible with the rest of the file?”

For actual structures and examples, continue with What Can Image Metadata Tell You About a Photo?.

JPEG recompression: a clue about file state, not intent

JPEG is lossy. Re-saving it performs another quantization step. Analysts can inspect quantization tables, block behavior and other compression-related patterns to form hypotheses about prior processing. But automatic platform processing can produce the same broad class of clue as a manual export. The final JPEG can tell you something about its current encoding state without reconstructing an entire edit history.

Resize and crop: geometry can matter more than appearance

Resizing creates a new sampling grid through interpolation. Cropping removes pixels and moves the coordinate frame of what remains. Those changes affect ordinary forensic measurements and also matter for invisible watermark systems whose detectors need to recover scale or alignment.

If a watermark check finds no signal, compare that result with the image’s transformation state. An unmarked image and a signal weakened beyond the detector’s validated range can lead to the same observation. Detection, payload recovery and historical interpretation are separate questions.

AI-generated or AI-edited images: system-specific evidence stays system-specific

There is no single universal technical clue that classifies every image as AI-generated or not AI-generated. Some ecosystems provide their own signals. Google’s SynthID, for example, can support checks for content produced or edited by supported Google AI systems; a negative result does not rule out other generators.

The same discipline applies to workflow metadata: a record shaped like a particular tool’s workflow is evidence about that record, not an all-purpose AI detector. Conversely, absence of that record is not proof that no AI system was involved.

Provenance is another evidence layer

C2PA Content Credentials use signed manifests and asset bindings to carry provenance assertions. When validation succeeds, they can help verify that specific assertions are bound to a particular asset state. They are not a universal truth score. Provenance, metadata, pixel-level clues and watermark signals can reinforce one another, but they should not be collapsed into one label.
