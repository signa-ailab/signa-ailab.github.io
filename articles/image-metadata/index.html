IMAGE METADATA

What Can Image Metadata Tell You About a Photo?

A digital photograph is not only a grid of pixels. Depending on the file format and the software that has handled it, the file may also carry structured information about capture settings, descriptive fields, editing software, workflow steps, or other technical context.

Published September 3, 2026 · SIGNA AI Lab

Metadata is not one thing

“Image metadata” is a convenient umbrella term, but it covers several standards and storage mechanisms that were designed for different purposes. Some fields originate with a camera. Others are written by photo-management or editing software. Still others may be added by a publishing workflow, a digital asset management system, or a generative-image tool.

This distinction matters because two fields that appear next to each other in a metadata viewer may have very different origins and levels of reliability. Reading metadata responsibly begins by identifying what structure the value came from, not merely by noticing that a value exists.

FamilyTypical roleExamples
EXIFCapture and camera-related information, plus other technical tags defined around the image-file workflowExposure settings, orientation, capture date/time, camera and lens fields
XMPExtensible metadata model used across creative, publishing, and asset-management workflowsCreator tool, dates, descriptions, rights-related or application-specific properties
IPTCProfessional descriptive, administrative, and rights-oriented photo metadataCaption, creator, location, keywords, credit and editorial fields
PNG text chunksTextual information stored directly in PNG chunksKeyword/value text, international text, compressed text, and application-defined workflow records

CIPA currently publishes the Exif 3.1 specification for digital still cameras. Adobe documents XMP as an extensible metadata platform standardized through ISO 16684, while IPTC maintains a photo-metadata standard used in professional imaging and publishing. PNG, meanwhile, defines text-bearing chunks such as tEXt, zTXt, and iTXt. These systems overlap in practice, but they are not interchangeable.

Capture information and workflow information answer different questions

Camera-origin fields can describe the circumstances recorded by the imaging device: shutter speed, aperture, orientation, date/time, camera model, lens information, GPS data when present, and other technical values. Even here, a field should be read as data stored in the file—not as an untouchable historical record. Metadata can be edited, copied between files, stripped, or rewritten.

Workflow metadata answers a different class of question. A field such as a software declaration or an XMP CreatorTool value may indicate that an application wrote its name into the file. That is useful context. It does not automatically establish that the named application originally created the image, that it performed a particular edit, or that no other software touched the file before or afterward.

Observation first, interpretation second.

“This file contains a declaration naming software X” is an observation. “Software X created this image” is a stronger historical claim and requires evidence that the metadata field alone does not provide.

Why software names can be informative—and misleading

Many applications write metadata when they save or export an image. A later application may preserve the earlier information, replace it, append new fields, or remove it entirely. As a result, a single file can contain records from several stages of a workflow, and the most visible software field may represent the last export rather than the beginning of the image’s history.

There is also no general rule that a missing software field means “no editing software was used.” Some applications write little metadata. Some export settings deliberately remove it. Messaging services, social platforms, screenshots, image converters, and privacy-cleaning tools can also change or discard fields.

What changes with AI-image workflows?

Some generative-image systems store structured workflow information that is more detailed than a simple software name. ComfyUI is a useful documented example: its Save Image node writes PNG files and can embed workflow metadata, including prompt-related information, for later reference. If such information remains in a file, it can reveal that the file contains a record shaped like a ComfyUI workflow.

That still does not turn the metadata into independent origin verification. A record can be copied, removed, altered, or attached to a derivative file. Conversely, an image generated with an AI system may contain no recognizable AI-workflow metadata after export, conversion, screenshotting, or platform processing.

For that reason, the safest language is specific: AI-workflow metadata was observed, a declared tool was observed, or no such record was observed in this check. None of those statements is equivalent to “AI-generated confirmed” or “not AI.”

PNG text metadata deserves separate attention

PNG does not use EXIF in exactly the same way as a typical JPEG workflow. The PNG specification defines textual chunks for storing keyword/value information. tEXt uses Latin-1 text, zTXt stores compressed textual data, and iTXt supports international UTF-8 text. Applications can use these containers for ordinary descriptions or for application-specific records.

This is one reason a metadata analyzer should not rely on a single parser or a single label called “metadata.” An informative review needs to know which container was parsed, whether the structure was valid, and what kind of field was actually observed.

Why metadata disappears or changes

A file’s metadata is not guaranteed to survive its entire life. Common transformations include:

  • saving or exporting through another application;
  • converting between JPEG, PNG, WebP, HEIC, or other formats;
  • recompressing or resizing an image;
  • creating a screenshot, which produces a new capture rather than copying the original file container;
  • uploading to a service that rewrites image files or removes selected metadata;
  • using a metadata-cleaning or privacy tool.

The visible image can look nearly identical while its metadata is substantially different. The reverse is also possible: metadata may be preserved even after the pixel data has been edited. This is why metadata should be treated as one evidence source among several, not as a complete timeline of everything that happened to an image.

A practical hierarchy for interpreting metadata

When reviewing an unfamiliar image, it helps to separate three levels:

LevelQuestionExample
1. ObservationWhat exact field or structure is present?An XMP CreatorTool value names an application.
2. ContextWhat workflow explanation is compatible with that observation?The application may have saved or exported this file at some point.
3. ConclusionWhat stronger claim would require additional evidence?Who created the image, whether a specific edit occurred, or whether the image is AI-generated.

Keeping these levels separate prevents a common analytical mistake: turning a valid technical observation into a historical or authorship claim that the data cannot support.

How SIGNA approaches metadata

SIGNA’s Image State Analyzer can surface available file information, including certain declared software or workflow-related observations when they are present. The product is designed to keep those observations separate from claims about ownership, originality, authorship, or AI generation.

An empty result is also deliberately narrow. If a particular field or workflow record is not found, the supported conclusion is only that it was not observed in that check. It is not a clearance that the image is unedited, authentic, or non-AI.

Metadata is valuable because it adds context—not because it settles every question.

The strongest analysis preserves the exact observation, understands how the field could have been written, and states the limit before drawing a broader conclusion.
