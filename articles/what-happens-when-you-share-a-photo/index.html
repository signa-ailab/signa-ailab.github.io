IMAGE SHARING & TRANSFORMATIONS

What actually happens to a photo when you share it?

A photo can look almost identical after it is sent through a messenger, uploaded to a social network, saved again, or captured as a screenshot. Under the surface, however, it may now be a different file: different dimensions, different compression, different metadata, and a different relationship to any watermark or provenance signal that existed before.

Published September 7, 2026 · SIGNA AI Lab

“The same photo” can be a different digital object

People usually judge sameness visually. If the face, room, product or landscape still looks the same, the photo feels unchanged. Computers can care about a different layer of identity. A byte-for-byte copy is one thing; a newly encoded JPEG that happens to look nearly identical is another.

Many sharing workflows create derivatives rather than preserving the original file exactly. A service may resize the image for a target display size, recompress it to reduce transfer cost, convert the format, remove or rewrite metadata, generate a preview, or produce several variants for different devices. A screenshot goes further: it captures rendered pixels into a newly created image rather than copying the original file.

Visual similarity does not imply file identity.

Two images can look indistinguishable at normal viewing size while having different bytes, metadata blocks, dimensions, compression histories and embedded-signal properties.

Think in layers: file structure, metadata, pixels and provenance

The easiest way to reason about sharing is to separate four layers that are often mixed together.

File structure is the container and encoded data: JPEG segments, PNG chunks, compression parameters, dimensions and other technical properties. Metadata is descriptive information stored in structures such as EXIF, XMP or IPTC. Pixel signal is the visual image data itself, including any invisible signal deliberately embedded into those pixels or transform coefficients. Provenance can involve signed records such as C2PA Content Credentials, which are a separate system for attaching verifiable assertions about an asset and its history.

These layers can fail independently. Metadata can disappear while the visible pixels remain. A pixel-domain watermark can be weakened even when some metadata survives. A signed provenance record may be detached from a derivative unless the workflow preserves or re-establishes the relevant binding. Treating all of these as “metadata” produces bad conclusions.

What happens when an app recompresses a JPEG?

JPEG does not store the image as raw RGB pixels. In simplified terms, the image is transformed into frequency coefficients and quantized. Re-encoding a JPEG means those values go through another lossy encoding step. Small details can be altered even when the visual result looks extremely close to the source.

This matters for forensic comparison and for invisible watermarks. An embedded signal may occupy subtle pixel or frequency patterns. Recompression can attenuate or reshape them. Whether the signal remains detectable depends on the watermark design, embedding strength, image content, payload, detector and compression setting. There is no honest universal rule that “JPEG destroys watermarks” or “watermarks survive JPEG.” The correct answer is conditional.

Recompression can also erase evidence of the previous encoding path. The new file tells you about its current encoding; reconstructing every earlier step from the final JPEG alone may not be possible.

Resizing changes geometry, not just sharpness

When an image is resized, interpolation constructs a new pixel grid. That affects texture and high-frequency detail, but it also changes geometry. For an invisible watermark detector, this can create a synchronization problem: even if parts of the signal remain, the detector may have to rediscover scale and alignment before it can read them.

For metadata, resizing is a different question. Some software preserves descriptive fields; other software writes a fresh file with a smaller subset. The pixel transformation itself does not logically require EXIF to vanish, but the export pipeline may choose not to carry it forward. That distinction is important: “resizing removes metadata” is not a law of image processing. It is a property of a particular workflow.

Cropping removes information permanently

A crop deletes pixels outside the selected region. Any signal that existed only in the removed area is gone. Distributed watermark systems can use redundancy so that part of a signal remains in the surviving region, but the detector now has less evidence and a shifted coordinate frame.

Cropping can also alter metadata or provenance depending on the editor. Some tools preserve camera metadata while recording that an edit occurred; others export a clean derivative. Modern provenance systems may append a new signed history entry rather than pretending the edited image is the original capture. These are workflow choices, not properties that can be inferred from the word “crop” alone.

A screenshot is not an ordinary copy

A screenshot records what was rendered on a display into a new image. The original file’s EXIF block is not simply carried over as part of that capture. The screenshot normally receives properties associated with the screenshot process and device, while the displayed content becomes pixels inside the new image.

That does not mean every kind of prior information becomes impossible to recover. A visible watermark remains visible if it appears in the captured region. An invisible watermark may or may not survive depending on scaling, display rendering, capture resolution and the detector. Some provenance ecosystems also combine embedded credentials with cloud lookup, fingerprinting or invisible watermarking so that associated records can sometimes be rediscovered even when embedded metadata is no longer present. Adobe, for example, documents possible-match recovery for Content Credentials stored in its cloud, including from screenshots.

A screenshot often breaks file continuity, but it does not justify a universal “all traces are gone” claim.

What remains depends on which layer carried the information and whether a matching or recovery system exists outside the original file.

Why social networks and messengers are hard to generalize

“Social media” is not one transformation. The same service may have different paths for feed uploads, stories, direct messages, original-quality attachments or downloaded copies. Mobile and web clients can behave differently. Platforms also change their media pipelines over time.

This is why platform-survival claims should be bounded by measured conditions. A test should state the platform, date, upload route, source dimensions, source format, quality setting and returned file. Results from one route should not silently become a permanent claim about the entire platform.

For users, the practical implication is simple: if preserving exact bytes matters, use a workflow designed to transfer the original file. If preserving contextual information matters, verify the returned file rather than assuming the platform carried everything forward.

What does disappearing metadata actually prove?

Very little by itself. Missing camera metadata can result from a privacy-oriented export, a screenshot, a social platform, an editor, a format conversion or a tool that simply never copied the fields. Its absence does not prove manipulation, AI generation, theft or malicious intent.

The reverse is also true. The presence of plausible EXIF does not prove that an image is an untouched camera original. Metadata can be copied, edited or reconstructed, and a valid-looking camera field does not independently authenticate the pixel history. Metadata is evidence about a file state or declared workflow, not a universal truth machine.

For a deeper explanation of these structures, see What Can Image Metadata Tell You About a Photo?

What does a missing invisible watermark prove?

Again, the answer is narrower than many product claims suggest. A failed detection can mean the image was never marked. It can also mean the signal was weakened, cropped away, geometrically desynchronized, tested with the wrong key or detector, or transformed beyond the system’s validated range.

A positive detection is also bounded. It can support a statement that a signal matching that system was observed under that check. It does not automatically prove legal ownership, originality, absence of editing or the identity of the person who published the file.

For the underlying engineering, see Invisible Watermarks in Images: How They Work and What Can Break Them.

Provenance systems answer a different question

C2PA Content Credentials are designed around cryptographically signed assertions and asset bindings. They can describe creation and editing context in a tamper-evident way. Importantly, the C2PA specification itself does not say that validated provenance makes the content “good,” “true” or trustworthy in every broader sense. It validates the relationship and integrity of the assertions that are actually present.

This distinction is useful because provenance, metadata and watermarking are complementary rather than interchangeable. Signed provenance can explain a declared chain. Metadata can expose capture or software context. Watermarks can provide a signal embedded in image content. None of these alone solves every authenticity question.

A practical checklist after receiving a shared image

Start with the file you actually received, not with assumptions about the sender’s original. Check dimensions and format. Inspect available metadata without treating missing fields as a verdict. If a specific watermark system is relevant, use its intended detector and note the transformation path if known. If Content Credentials or another provenance mechanism is present, validate it using the appropriate inspection tool. Compare against a known original only when you truly have a trusted reference.

Most importantly, keep conclusions proportional to evidence. “This returned JPEG is smaller and has no EXIF” is an observation. “Therefore the image is fake” is a leap.

How SIGNA fits into this picture

SIGNA separates these layers rather than treating them as one score. It can add visible watermarks and an invisible SIGNA signal, and its Inspect flow presents signal-related and image-state information on device. When a visible watermark is applied, SIGNA also adds the invisible SIGNA signal. For JPEG images, the current SIGNA signal uses a DCT-based frequency-domain approach.

SIGNA does not interpret an invisible-signal result as legal proof, ownership proof, originality proof or an AI-generation verdict. Sharing transformations such as recompression, resizing, cropping, screenshots and platform processing can affect what can be detected or recovered. Those boundaries are part of the product’s technical meaning, not footnotes to be hidden.

The right question after sharing is not “Did the photo stay the same?”

Ask instead: which layer changed, which layer survived, what evidence is actually present in the file I have now, and what conclusion does that evidence legitimately support?
